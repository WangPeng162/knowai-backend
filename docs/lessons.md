# KnowAI · 踩坑与经验沉淀

> 开发过程中真实踩过的坑与做出的设计决策。既是复盘文档，也是面试中"你遇到过什么难题、怎么解决的"素材库。
> 记录格式：**现象 → 根因 → 解决 → 教训**。

---

## 一、RAG 检索质量（数据驱动优化）

### 1. 切分质量是检索的地基 —— 一次改动带来 +20% @1

- **现象**：chunk 里出现"…高级职称**师578人**"这类残块——一句话被从中间劈开。
- **根因**：切分器名为"递归切分"，实际是**固定 800 字符硬切**，完全不看语义边界。答案被劈成两半后，embedding 语义残缺，任何排序手段都救不回来。
- **解决**：改用 LangChain4j `DocumentSplitters.recursive(800, 100)`——按"段落 → 句子 → 词 → 字符"的层级递归寻找语义边界；每页独立切分以保持 `pageNumber` 归属正确。
- **数据**：HitRate@1 从 60% → **80%**，且**纯 embedding 直排的 @1 也从 45% → 50%**（不靠 rerank 也变好）。
- **教训**：**先修地基（数据质量），再上花活（排序模型）**。地基没修时上 rerank，收益会被数据问题吃掉。

### 2. rerank 治排序、不治召回

- **做法**：embedding 粗召回 Top-20（保召回）→ rerank 精排取 Top-2（提精度）。
- **数据**：@1 45%→60%、@2 75%→90%，但 **@5 完全不变**（95%）——因为答案本来就在召回池里，rerank 只是把它往前顶。
- **教训**：**召回率和精度是两个独立问题**。rerank 救不了"答案根本没召回"的场景，那时该查切分和检索范围。

### 3. Query Rewriting：检索层与生成层的"记忆断层"

- **现象**：多轮对话第二问"它有什么缺点？"——模型（有记忆）能看懂"它"，但**它把这句话原样传给了检索工具**，embedding 拿一个没有语义锚点的代词去检索，全部落空。
- **根因**：记忆只服务于"生成层"；检索层是无状态的"哑巴"，不参与对话。
- **解决**：新增 `QueryRewriter` 组件——检索前用 LLM 结合最近对话历史把问题改写为"自包含"的完整问题（"RAG 有哪些缺点？"）；无历史时直接跳过（省一次 LLM 调用）；改写失败/返回空白则降级用原问题。
- **数据**：指代题 HitRate@1 从 33% → **100%**，MRR 0.58 → 1.00；其中一题从 rerank rank4（@2 miss）直接提到 rank1。
- **教训**：**改写只影响"检索输入"，不改变用户看到的内容**——它是检索层的内部预处理，用户无感知。

### 4. 评估集必须和文档版本绑定（删文档 = 删答案）

- **现象**：评估集里一题始终答不出（关键词 19002），把题目关键词改成文档里的"两万多人"后**仍然 miss**。
- **根因**：排查发现该答案文本**只存在于一份已删除的旧版文档**中，当前版本文档全文根本没有这个数据——删文档时顺手把"标准答案"删了。
- **解决**：换用当前文档中确实存在的事实出题；并确立规则——**任何文档删除/替换前，先检查评估集中哪些题依赖它**。
- **教训**：评估集不是孤立资产，它与数据源存在**隐式依赖**；文档治理要连评估集一起治理。

### 5. RAG 的典型失败模式（实测记录）

| 失败模式 | 表现 | 应对 |
|---------|------|------|
| 数据缺失 | 库里没这个信息 → 模型正确回答"资料中没有" | ✅ 这是好行为，别改 |
| Agent 该调工具却不调 | 凭预训练记忆硬答 | System Prompt 强约束"事实性问题必须检索" |
| 概率性行为 | 同一问题有时调工具、有时不调 | 无法根治，靠更强模型/降温度 |
| 张冠李戴 | 读 A 校文档，答出 B 校信息（预训练印象干扰） | 元数据约束 + 更强模型 + 关键对话换新会话 |
| 多轮会话漂移 | 同一会话历史污染后续问答 | 关键对话新开会话 / 定期清理记忆 |

## 二、工程与架构

### 6. 跨数据源删除的"顺序铁律"

- **背景**：一个文档对应 MySQL 里的 chunk + Qdrant 里的向量 + 两者之间的映射表。
- **铁律**：删除时必须 **先删 Qdrant 向量 → 再删映射记录 → 最后删 chunk**。
- **为什么**：`vectorId` 是通过 chunkId 查映射表得到的；如果先删 chunk，映射关系断裂，Qdrant 里的向量就变成**永远找不到、也删不掉的孤儿数据**（占空间且可能被检索到）。
- **实现**：`deleteEmbeddingByDocumentId` 里严格按此顺序；知识库删除则循环复用文档删除，保证每个文档都走同一套清理逻辑。

### 7. 用"编排层"规避循环依赖

- **现象**：要新增"删除知识库"，它需要调用"删除文档"的能力——但 `KnowledgeDocumentServiceImpl` 已经注入了 `KnowledgeService`（查归属用），反向注入立刻形成**构造器循环依赖，Spring 启动失败**。
- **解决**：不硬塞进已有的基础 Service，而是新建独立编排层 `KnowledgeEditService`——它依赖别人、不被别人依赖，天然无环。
- **教训**：分层要看**依赖方向**。基础服务之间的横向互调往往是设计信号：该抽一个上层编排者了。

### 8. 跨数据源不加事务（显式取舍）

- **决策**：删除类操作**不加 `@Transactional`**。
- **理由**：操作同时涉及 MySQL 与 Qdrant，事务只能回滚 MySQL，**Qdrant 里已删的向量回不来**——加了反而制造"很安全"的错觉。
- **替代**：靠"顺序 + 幂等 + 补偿清理"控制风险，并把这一取舍显式写进代码注释和文档。

## 三、Bug 速查（真实踩过的坑）

### 9. "空集合"陷阱的三种形态

同一个思维漏洞在不同 API 上的三种表现，**结局都是灾难性的**：

| 场景 | 空集合的行为 | 后果 |
|------|------------|------|
| MyBatis-Plus `.in(空集合)` | 条件被移除 | **退化成全表查询/更新** |
| Qdrant 检索不带 filter | 等于不过滤 | **搜到全库（含他人知识库）** |
| Qdrant `removeAll(空列表)` | 客户端校验失败抛异常 | **删除流程整体中断** |

- **教训**：**任何"集合参数传给外部 API"的调用点，都要先问一句"如果它是空的会怎样"**；能提前拦截就提前拦截（卫语句早返回）。

### 10. 包装类型比较：`==` 还是 `equals`？

- **现象**：权限校验里 `Long` 类型的 userId 用 `==` 比较，偶发判断错误。
- **根因**：`Long` 是对象，`==` 比的是**引用**；小数值（-128~127）因缓存偶然相等，超出范围立刻出错。
- **解决**：统一用 `Objects.equals(a, b)`（同时解决 null 安全）。**教训：包装类型一律不用 `==`。**

### 11. txt 文件解析必崩：`pageNumber` 为 null

- **现象**：上传 .txt 文件解析必失败（PDF 一直正常）。
- **根因**：`TxtParser` 里 `page.setPageNumber(null)`（txt 没有"页"的概念），这个 null 一路传到向量化的 `metadata.put("pageNumber", null)` → NPE。
- **解决**：txt 统一记为第 1 页；并在向量化处对历史 null 数据加兜底。**教训：可空字段要往"下游全部消费点"看一遍。**

### 12. 越权漏洞三连（同一种错误的三层表现）

- **文档层**：上传/列表/详情接口只校验"知识库存在"，**不校验归属** → 任何登录用户可查看他人知识库文件。
- **问答层**：`/chat` 未校验 `knowledgeId` 归属 → **可直接套取他人知识库内容**。
- **全局检索层**：不传 `knowledgeId` 时无任何过滤 → 变成了**全站所有用户所有知识库**的检索。
- **统一解决**：抽出 `checkKnowledgeOwnership(knowledgeId)`（"文档 → 知识库 → 用户"归属校验）挂到全部入口；"不传知识库"语义收紧为"**我的全部知识库**"（用 `knowledgeId IN (自己所有库)` 过滤 + 空范围早返回）。
- **教训**：**校验要按"数据流向"逐个入口排查**，补了一处不等于补完；测试要构造"另一个账号"去做对抗验证。

### 13. LangChain4j 1.x 的 API 记忆偏差

- `ChatModel.chat()` 返回的是 `dev.langchain4j.model.chat.response.ChatResponse`（注意包名里有 `response`）。
- 存在两个同名 `SystemMessage`：`dev.langchain4j.service.SystemMessage`（AiServices 注解）vs `dev.langchain4j.data.message.SystemMessage`（消息类型），import 极易写错。
- **教训**：第三方库的包路径不要凭记忆写，**以 IDE 补全/编译结果为准**。

### 14. git 误删目录的恢复

- **事故**：清理"重复目录"时删错了——删掉的是**最新代码**，仓库里留的是远程旧版，导致多个模块丢失。
- **恢复**：从 git 历史提交中找回文件，逐一恢复。
- **教训**：`git rm -rf` 前**先看内容判断哪边是新版**（判断依据是"新功能在不在"，不是目录名）；删前先 `git status` 确认影响面。

### 15. 配置丢失的排查路径

- **现象**：应用启动连数据库报 `Access denied ... (using password: NO)`。
- **含义**：**Spring 没加载到数据源账号密码**（不是密码错，而是压根没读到配置）。
- **排查顺序**：① `src/main/resources/` 下本地配置文件是否存在 → ② 是否被 git 操作误移/删除 → ③ 打包产物内是否包含该配置。
- **教训**：把"错误信息 → 可能原因清单"沉淀成排查路径，下次同类问题 1 分钟定位。

## 四、RAG 边界控制与上线部署（2026-09 新增）

### 16. 域外拒答：无关问题为什么总会"被回答"

- **现象**：线上问"如何赚钱"（知识库里没有）→ AI 用自己的预训练知识答了一整套方案，还附上两条 58% 相似度的无关引用。
- **根因（三层）**：
  1. **向量检索"永远有结果"**：本质是"返回最相似的 Top-K"，**无论问题多离谱都会返回 K 个片段**（实测无关问题也拿到 58.9% 的内容），模型误以为"有依据"。
  2. **Prompt 没约束"资料不相关时怎么办"**：只写了"事实性问题必须查工具"，没写"查不到必须拒答、严禁用自有知识"。
  3. **没有相关性门槛**：rerank 分数 0.58 明显偏低，但系统里没有任何机制说"低于 X 分就是没命中"。
- **解决（软硬双管）**：
  - **软**：SystemMessage 明确"只能依据资料作答；资料无关必须回答'知识库中没有相关信息'；严禁用自有知识补充"。
  - **硬**：`KnowledgeSearchTools` 加 `SCORE_THRESHOLD = 0.3` —— rerank 分数低于阈值直接丢弃、不喂给模型；全部低于阈值则直接返回"资料中没有相关信息"。
- **第二层坑（实测才暴露）**：堵住"事实性问题"后，**情感/闲聊类仍然漏网**（"我爱你""我今天心情不好""陪我聊天"）——模型把它们归为"非事实性提问"，于是切到安慰/陪聊模式。补规则 6（禁止闲聊/情感交流/陪聊）后才彻底堵住。
- **教训**：
  - RAG 的边界要**软约束 + 硬门槛双管齐下**，只靠模型自觉不可靠。
  - **"拒答"是正确的产品行为**——要在 prompt 里明确告诉模型"说不知道不算失败"。
  - 约束类改动必须**双向验证**：该拒绝的拒了，该回答的还要能答。

### 17. 改完东西必须跑评估回归（别靠"感觉没问题"）

- **场景**：改了 prompt + 加了检索阈值，怎么确认没把正常问答改坏？
- **做法**：跑评估集（`mvnw test -Dtest=EvalRunner`），对比 HitRate@1/@2/MRR。
- **结果**：**无退化**（Q1-Q20 仍是 @1 85% / @2 100%，指代题 rewrite 后 100%）→ 阈值 0.3 没有误伤正确答案。
- **教训**：
  - 有评估集就用数字说话，**"我感觉没问题"是最贵的四个字**。
  - 看数字要**注意统计口径**：本次汇总把"20 道知识题 + 3 道指代题"混在一个分母里，@1 显示 78.3%（看起来像从 85% 掉了），分开算其实完全一致——**误读比没数据更危险**。

### 18. Prompt 也是"数据"：源码拼接符混进了提示词

- **现象**：Agent 判断力莫名下降——域外拒答不生效、该调工具时偶尔不调。
- **根因**：把 `@SystemMessage` 的**实际字符串**打出来看，发现源码的拼接符号被写进了字符串字面量：

  ```
  你是一个知识库助手。" +
          "凡是涉及具体学校、人物、事件、数据、定义等需要准确信息的，" +
          "        "**必须先**调用 searchKnowledge 工具查询。" +
  ```

  模型收到的就是这堆"带引号、加号、缩进的乱文本"——**提示词被污染了**。
- **解决**：改用 Java 文本块（`"""`）重写，语义清晰、不会再混入源码符号。
- **教训**：
  - **prompt 是喂给模型的数据，不是代码**。多行文本用文本块/模板/配置文件，别手工拼字符串。
  - 这类 bug **编译不报错、测试不报错**，只能靠"**看模型实际收到了什么**"发现 —— **prompt 也要可观测**。

### 19. 国内服务器拉不到 Docker Hub 镜像（403）

- **现象**：`docker pull mysql:8.0` 卡住/超时；配了阿里云镜像加速器后变成 `403 Forbidden`。
- **根因**：阿里云加速器的定位是"加速**你自己推到 ACR 的私有镜像**"，**不服务 Docker Hub 公共镜像**（官方公告也写着"仅限特定范围"）。这不是配置错，是**工具用途不对口**。
- **解决**：**镜像搬运** —— 本机（能拉）`docker save` 导出 → `scp` 上传 → 服务器 `docker load` 导入。**完全不依赖网络镜像源**，这是离线部署/内网部署的标准做法。
- **教训**：拉不到镜像时，"**搬运**"比"换源"更可靠；思路和"离线安装包"一样。

### 20. compose 默认镜像名依赖"目录名"

- **现象**：把本机构建的镜像搬到服务器后，`docker compose up -d` 仍尝试重新构建（然后失败）。
- **根因**：compose 默认镜像名是 `<项目名>-<服务名>`，**项目名默认取当前目录名**——本机目录 `KnowAI` 与服务器目录 `knowai-backend` 生成的镜像名不同，搬过去的镜像"对不上号"。
- **解决**：在 compose 里**显式写 `image: knowai-backend:latest`**，两个环境强制同名。
- **教训**：**依赖"隐式默认值"的配置，换个环境就会变**。关键标识要显式声明，别让环境决定你的构建产物名。

### 21. 502 的误判：中间层会伪造症状

- **现象**：外网访问一直返回 `502 Bad Gateway`，看起来像"后端崩了"。
- **真相**：本机开着代理，**502 是代理返回的**；服务器上其实是"防火墙没放行 8000，请求根本没到后端"。
- **正解**：**在服务器本地 `curl localhost:端口` 验证** —— 绕开所有中间层（代理 / 公网 / DNS / 防火墙），从"离服务最近的地方"开始查。
- **教训**：排查网络问题要**从近到远分层验证**：容器内 → 宿主机 → 局域网 → 公网。**每一层都可能伪造症状**。

### 22. 环境隐式依赖：忘了建 Qdrant 集合

- **现象**：线上解析文档必失败（`status=3`），日志报 `NOT_FOUND: Collection 'knowai_knowledge' doesn't exist`。
- **根因**：**本机那个集合是项目早期手动建的**，而新服务器上的 Qdrant 是全新空的 —— 代码假设"集合已存在"。
- **解决**：手动创建（维度必须与 embedding 模型输出一致）：

  ```bash
  curl -X PUT http://localhost:6335/collections/knowai_knowledge \
    -H 'Content-Type: application/json' \
    -d '{"vectors":{"size":1024,"distance":"Cosine"}}'
  ```

- **教训**：**部署 = 在新机器上重建"本机靠手工做过的一切"**。上线前必须盘点这类隐式依赖：

  | 依赖 | 本机怎么来的 | 新环境怎么解决 |
  |------|-------------|--------------|
  | MySQL 表结构 | 手动建库 | ✅ 导出 `schema.sql`，容器首启自动执行 |
  | **Qdrant 集合** | 手动建 | ❌ **漏了（这就是事故）** |
  | OSS bucket | 手动建 | ✅ 外部服务，早已存在 |
  | 环境变量/密钥 | 本地配置文件 | ✅ 写入 `.env` 注入 |

### 23. 部署成本优化：让服务器自己构建

- **问题**：服务器下行只有 153KB/s，**改一行代码要传 407MB 的镜像 ≈ 40 分钟** —— 迭代一次浪费半天。
- **解决**：把**构建用基础镜像**（maven / temurin-jre / node / nginx，约 1GB）**一次性**搬到服务器 → 以后服务器用**源码**自己 `docker compose build`。
- **效果**：构建 **165 秒**；改代码上线循环 ≈ **3 分钟**（只传 KB 级源码，且只重建变化的服务）。
- **教训**：**先优化"迭代循环"，再优化"功能"**。如果每次改动都要等 40 分钟，任何技术优化都会被这个摩擦成本吃光。

### 24. SSH 会话会超时断连

- **现象**：长时间操作/传大文件后 SSH 突然断开（`client_loop: send disconnect: Connection reset`）。
- **真相**：正常的会话超时。**已传完的文件不受影响**（文件在服务器磁盘上，和会话无关）。
- **进阶处置**：长任务用 `tmux`/`screen` 托管（断开也不中断任务）；或调大 `sshd_config` 的 `ClientAliveInterval`。
- **教训**：别把"会话中断"误判成"操作失败" —— 先确认结果（`ls` / `docker compose ps`），再决定要不要重做。

## 五、一句话总结

> **数据质量决定上限，工程规范决定下限，评估体系决定你能不能知道自己在哪。**
